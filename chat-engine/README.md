# chat-engine

موتور پاسخگوی هوشمند چندلایه‌ی فروشگاه — کاملاً **مستقل** از بک‌اند اصلی
(پوشه‌ی ریشه‌ی این ریپازیتوری). تنها ارتباط این سرویس با بک‌اند، خواندنِ
**مستقیم** از دیتابیس Postgres همان بک‌اند است (SQL خام، بدون API، بدون
Prisma)، تا در آینده اگر لازم شد بشود همین موتور را بدون تغییر کد، برای
بک‌اند/کسب‌وکار دیگری هم نصب کرد (چند-مستاجری).

## پشته‌ی فنی و چرایی آن

| لایه | تکنولوژی | چرا |
|---|---|---|
| HTTP framework | **NestJS روی Fastify** | Express برای یک موتور چت-محور و real-time مناسب نیست. NestJS ساختار (ماژول/DI/Guard/Pipe/Gateway) می‌دهد که با رشد موتور (کانال‌های بیشتر، چند-مستاجری) لازم می‌شود؛ آداپتور Fastify هم سرعت/overhead کمتر HTTP را می‌دهد — بدون این‌که ساختار Nest را از دست بدهیم. |
| Real-time | **Socket.io + Redis adapter** | چت زنده باید واقعاً لحظه‌ای باشد. آداپتور Redis برای وقتی لازم است که موتور روی چند نمونه (instance) هم‌زمان اجرا شود — بدون آن، پیام یک اپراتور روی سرور A به مشتری وصل‌شده به سرور B نمی‌رسد. |
| دیتابیس خودِ موتور | **MongoDB** | مکالمات/پیام‌ها داده‌ی محاوره‌ای و سندمحورند؛ برای این نوع داده مناسب‌تر از یک دیتابیس رابطه‌ای است. |
| خواندن از فروشگاه | **SQL خام (`pg`)، بدون Prisma** | بدون وابستگی به کلاینت تولیدشده یا نسخه‌ی خاصی از اسکیمای بک‌اند؛ یعنی می‌شود همین کد را روی چند بک‌اند/تنانت مختلف (با شکل جدول‌های مشابه) اجرا کرد، فقط با یک connection string متفاوت. |
| Redis (کش/rate-limit) | **ioredis** | کش کوتاه‌مدت و محدودکننده‌ی نرخ فراخوانی لایه‌ی AI (که هزینه‌ی واقعی دارد) — جدا از نقش Redis در Socket.io. |

> چرا نه GraphQL جلوی Postgres؟ چون یا باید یک سرویس جدا (Hasura/PostGraphile)
> per-tenant نصب کرد که با هدف «نصب ساده بدون انتقال کد» در تضاد است، یا
> resolver هایی که همچنان مستقیم به همان Postgres وصل‌اند و هیچ کلاینت
> بیرونی هم قرار نیست از این GraphQL استفاده کند — یعنی overhead بدون فایده.
> همان کاری که GraphQL می‌کرد (انتزاع از شکل جدول‌های هر تنانت) را همین حالا
> `engine/productMatcher/*` با SQL خام انجام می‌دهد.

## معماری لایه‌های پاسخگویی

- **لایه ۱ — کلمات رزرو شده** (`src/engine/layer1-keywords`): تشخیص intent
  (قیمت/موجودی/رنگ/سایز/برند/تخفیف/نحوه‌سفارش/ارسال) و پاسخ مستقیم از
  دیتابیس فروشگاه. محصول از روی «کد کوتاه محصول» (`Product.shortCode` —
  زیر بیوگرافی/کپشن، فقط در کانال‌های اجتماعی معنا دارد) یا جست‌وجوی فازی
  پیدا می‌شود. **مکالمه‌آگاه است، نه فقط پیام‌به‌پیام**:
  - اگر پیام قبلی موتور منتظر جواب خاصی بود (کد محصول یا انتخاب از یک
    لیست)، پیام بعدی مشتری — حتی اگر فقط «۲» یا «دومی» یا خودِ کد کوتاه
    باشد — به همان سوال پاسخ داده می‌شود، نه به‌عنوان یک پیام تازه و
    بی‌ربط (`ConversationContext.pendingAction`، ثبت‌شده روی همان
    ConversationMessage که سوال را پرسیده).
  - آخرین محصولی که در مکالمه شناسایی شد به خاطر سپرده می‌شود
    (`Conversation.lastProductId`) — یعنی «قیمتش چنده؟» بعد از چند پیام
    «رنگاش چی داره؟» بدون تکرار کد هم درست جواب داده می‌شود.
  - متن پاسخ‌ها بر اساس کانال فرق می‌کند: ویجت وب‌سایت هیچ‌وقت از
    «فوروارد پست» یا «کد زیر بیوگرافی» حرف نمی‌زند (این مفاهیم آنجا
    اصلاً وجود ندارند)، برخلاف تلگرام/اینستاگرام/واتساپ/بله.
- **لایه ۲ — هوش مصنوعی** (`src/engine/layer2-ai`): وقتی لایه ۱ جوابی
  نداشت. context فقط از دیتابیس فروشگاه ساخته می‌شود (همان
  `lastProductId` هم اینجا به‌عنوان fallback استفاده می‌شود) و به مدل
  گفته می‌شود فقط از همان استفاده کند، وگرنه اطمینان کم گزارش بدهد.
  **کاملاً از env کنترل می‌شود** — `AI_PROVIDER` یکی از: `anthropic`,
  `openai`, `deepseek`, `openrouter`, `kilo`, `google`, `custom`. همه به‌جز
  anthropic یک API سازگار با OpenAI (`/chat/completions`) دارند؛ فقط
  `baseUrl`/`apiKey`/`model` فرق می‌کند (`custom` برای هر gateway دیگری که
  در لیست نیست). جزئیات و مثال هر کدام: `.env.example`.
- **لایه ۳ — اپراتور**: اگر اطمینان لایه ۲ کمتر از `AI_CONFIDENCE_THRESHOLD`
  باشد، وضعیت مکالمه `NEEDS_OPERATOR` می‌شود و در صف real-time اپراتور
  (namespace `/operator`) ظاهر می‌شود.

`engine/*` عمداً **framework-agnostic** نوشته شده (بدون هیچ import ای از
Nest) — فقط تابع‌های خالص که با `ProductLookupPort` کار می‌کنند، نه مستقیم
با `pg.Pool`. این یعنی مستقیماً و سریع قابل تست هستند (`tests/`)، و اگر
روزی فریم‌ورک عوض شد، منطق اصلی دست‌نخورده می‌ماند.

### محافظت از دیتابیس فروشگاه در برابر ترافیک بالا

چون خواندن مستقیم از Postgres است (بدون کش API میانی)، اگر هزاران نفر
هم‌زمان قیمت/موجودی یک محصول را بپرسند، بدون محافظت هرکدام مستقیم یک کوئری
جدید می‌زدند. دو مکانیزم مکمل این را کنترل می‌کند
(`src/store/cached-product-lookup.ts` + `src/redis/redis-cache.service.ts`):

1. **کش Redis با TTL کوتاه (۲۰ ثانیه برای قیمت/موجودی/جست‌وجو):** بار دوم
   به بعد اصلاً کوئری‌ای به Postgres نمی‌رود. کلیدها tenant-scoped هستند.
2. **هم‌بسته‌سازی درخواست‌های هم‌زمان (request coalescing):** دقیقاً برای
   لحظه‌ای که کش هنوز خالی است و مثلاً ۱۰۰۰ نفر هم‌زمان می‌پرسند — همه‌شان
   منتظر همان یک کوئری در حال اجرا می‌مانند، نه هزار کوئری جدا (تست
   `tests/redisCacheService.test.ts` دقیقاً همین سناریو را با ۱۰۰۰ درخواست
   هم‌زمان شبیه‌سازی و اثبات می‌کند). این کوالسینگ در سطح هر instance است؛
   بین چند instance، کش Redis همان اثر را با تاخیر خیلی کم می‌دهد.

نکته: این تضمین ۱۰۰٪ نیست (یک پنجره‌ی زمانی خیلی کوتاه بین چک‌کردن کش و
ثبت‌شدن در نقشه‌ی in-flight وجود دارد)، اما دامنه‌ی مشکل را از «هزاران
کوئری هم‌زمان» به «چند کوئری» کاهش می‌دهد که برای این حجم کاملاً کافی است.
اگر روزی لازم شد، می‌شود با یک قفل توزیع‌شده‌ی Redis (`SET NX`) این را
کاملاً تضمینی هم کرد.

علاوه بر این، اندازه‌ی Pool اتصال Postgres هر تنانت با `STORE_DB_POOL_MAX`
قابل تنظیم است — کش اکثر ترافیک تکراری را جذب می‌کند، اما یک موج سوال
درباره‌ی محصولات کاملاً متفاوت هنوز به همین pool می‌رسد.

### چند-مستاجری در آینده

کل داستان چند-مستاجری‌شدن یک کالکشن Mongo به اسم `tenants` است: هر سند یک
`key` + connection string دیتابیس Postgres همان کسب‌وکار. اضافه‌شدن مستاجر
جدید = یک سند جدید، بدون هیچ تغییر کدی. `src/tenancy/tenant-resolver.middleware.ts`
تنها جایی است که باید هدر/دامنه برای تشخیص تنانت هر درخواست HTTP گسترش
داده شود؛ گیت‌وی‌های WebSocket مستقیم `tenantKey` را در query می‌گیرند.

## راه‌اندازی

```bash
cd chat-engine
cp .env.example .env   # مقادیر را پر کنید
npm install
npm run dev
```

پیش‌نیازها: MongoDB (`MONGO_URI`)، Redis (`REDIS_URL`)، و دسترسی خواندنی
به همان Postgres بک‌اند اصلی (`DEFAULT_TENANT_STORE_DATABASE_URL`).

⚠️ برای تشخیص محصول از روی کد کوتاه، ستون `shortCode` باید روی جدول
`Product` بک‌اند اصلی وجود داشته باشد — این فیلد به `prisma/schema.prisma`
**پروژه‌ی اصلی** اضافه شده؛ برای اعمال آن روی دیتابیس واقعی در پروژه‌ی اصلی:

```bash
npx prisma migrate dev
npx prisma generate
```

## API

**ویجت چت سایت:**
- `POST /api/chat/messages` — ارسال پیام `{ guestToken, text, displayName? }` (اگر مکالمه دست اپراتور باشد، `reply: null` برمی‌گردد — رجوع به «رفتار sticky» پایین)
- `GET /api/chat/messages?guestToken=...` — تاریخچه‌ی مکالمه

**پنل اپراتور** (نیازمند توکن پنل ادمین سایت اصلی؛ راهنمای کامل: [`docs/OPERATOR_INTEGRATION.md`](./docs/OPERATOR_INTEGRATION.md)):
- `GET /api/operator/queue?status=&channel=` — لیست مکالمات با فیلتر آزاد روی status/channel (بدون status، پیش‌فرض صف کلاسیک NEEDS_OPERATOR/WITH_OPERATOR)
- `GET /api/operator/conversations/:id` — پیام‌های یک مکالمه
- `POST /api/operator/reply` — پاسخ اپراتور `{ conversationId, text }`
- `POST /api/operator/conversations/:id/close` — بستن مکالمه
- `POST /api/operator/conversations/:id/release` — آزادکردن مکالمه (برگشت به حالت خودکار — تنها راه خروج از NEEDS_OPERATOR/WITH_OPERATOR)
- `DELETE /api/operator/conversations/:id` — حذف کامل مکالمه
- `GET /api/operator/conversations/:id/messages/:messageId/media` — پروکسی رسانه‌ی تلگرام (عکس/صوت) بدون ذخیره‌سازی

Socket.io:
- namespace `/chat` (کوئری `guestToken`؛ رویداد `message:send` → `engine:reply` / `operator:reply` / `message:received`) برای ویجت سایت
- namespace `/operator` (هندشیک با `auth.token`؛ رویدادهای `queue:new` / `queue:update` / `queue:removed` لحظه‌ای، و `operator:reply` هم قابل emit از همین‌جاست — نیازی به REST جدا نیست)

### رفتار «sticky» — یک باگ مهم که رفع شد

به محض این‌که یک مکالمه `NEEDS_OPERATOR` یا `WITH_OPERATOR` شد، لایه‌های
خودکار (۱ و ۲) دیگر **هیچ‌وقت خودشان دوباره وارد نمی‌شوند** — حتی اگر پیام
بعدی مشتری دوباره یک کلمه‌ی رزرو شده داشته باشد. قبلاً این‌طور نبود: هر
پیام تازه، صرف‌نظر از وضعیت مکالمه، از لایه ۱ رد می‌شد. تنها راه برگشت به
حالت خودکار، `POST /api/operator/conversations/:id/release` است.

## کانال‌ها

- **وب‌سایت** — چت زنده با Socket.io، بدون مفهوم «ریپلای به یک پیام
  مشخص» (فقط لیست خطی پیام‌ها). راهنمای کامل فرانت‌اند:
  [`docs/FRONTEND_INTEGRATION.md`](./docs/FRONTEND_INTEGRATION.md)
- **تلگرام** — وصل شده (حالت polling برای توسعه، آماده برای سوییچ به
  webhook در تولید بدون تغییر کد). یک منوی دکمه‌ی سریع دارد (جستجوی
  محصول/بررسی موجودی/استعلام قیمت/تماس با پشتیبانی)، پاسخ اپراتور به‌صورت
  بومی روی پیام مشتری quote می‌شود (reply threading)، و عکس/صوت بدون
  ذخیره‌سازی مستقیم به اپراتور ارجاع داده می‌شود. راهنما:
  [`docs/TELEGRAM_SETUP.md`](./docs/TELEGRAM_SETUP.md)

## هنوز اضافه نشده (تسک‌های بعدی)

- اتصال به API رسمی اینستاگرام/واتساپ/بله (همان الگوی تلگرام: وبهوک‌ها به
  همین `MessageService.processIncomingMessage` مشترک وصل می‌شوند)
- ثبت سفارش از داخل چت
- پنل مدیریت تنانت‌ها (فعلاً فقط از طریق دیتابیس)
