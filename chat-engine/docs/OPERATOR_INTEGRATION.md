# راهنمای اتصال پنل ادمین/اپراتور به chat-engine

این سند برای کسی است که پنل مدیریت مکالمات (صف اپراتور) را می‌سازد —
جدا از `FRONTEND_INTEGRATION.md` که برای ویجت چت مشتری‌هاست.

---

## احراز هویت

نیازی به لاگین جداگانه نیست — همان access token ای که پنل ادمین سایت اصلی
صادر می‌کند (JWT با `JWT_ACCESS_SECRET` مشترک) اینجا هم معتبر است. نقش
کاربر باید یکی از `ADMIN`, `EDITOR`, `SUPPORT` باشد.

```
Authorization: Bearer <همان access token پنل ادمین>
```

برای Socket.io همین توکن در `auth.token` هندشیک فرستاده می‌شود (پایین‌تر).

---

## ۱. لیست مکالمات — REST (بارگذاری اولیه)

### `GET /api/operator/queue`

اولین باری که پنل باز می‌شود، لیست را از همین‌جا بگیر. بعد از آن دیگر
نیازی به رفرش/poll نیست — Socket.io آپدیت‌های بعدی را لحظه‌ای می‌فرستد
(بخش ۲).

**فیلترها (Query Params، همه اختیاری):**

| پارامتر | مقادیر | توضیح |
|---|---|---|
| `status` | `OPEN`, `AI_HANDLING`, `NEEDS_OPERATOR`, `WITH_OPERATOR`, `CLOSED` (با کاما هم می‌شود چندتا داد) | **بدون این پارامتر، همه‌ی مکالمات نشان داده می‌شوند** — چت‌های مشتری با بات را هم شامل می‌شود، نه فقط صف اپراتور. برای دیدن فقط چت‌های نیازمند پشتیبانی: `status=NEEDS_OPERATOR,WITH_OPERATOR` |
| `channel` | `WEBSITE`, `INSTAGRAM`, `WHATSAPP`, `TELEGRAM`, `BALE` | فیلتر روی یک کانال خاص |

مثال‌ها:
- `GET /api/operator/queue` → همه‌چیز (چت‌های خودکار با بات را هم می‌بینی)
- `GET /api/operator/queue?status=NEEDS_OPERATOR,WITH_OPERATOR` → فقط صف نیازمند پشتیبانی
- `GET /api/operator/queue?status=CLOSED&channel=TELEGRAM` → تاریخچه‌ی بسته‌شده‌های تلگرام

**پاسخ:**
```json
{
  "success": true,
  "data": [
    {
      "id": "665f...",
      "channel": "TELEGRAM",
      "status": "NEEDS_OPERATOR",
      "customer": { "_id": "665f...", "displayName": "علی", "externalId": "123456789" },
      "lastMessageAt": "2026-08-06T10:00:00.000Z"
    }
  ]
}
```

### `GET /api/operator/conversations/:conversationId`

تاریخچه‌ی کامل پیام‌های یک مکالمه (وقتی اپراتور روی یک آیتم از لیست کلیک
می‌کند).

---

## ۲. آپدیت لحظه‌ای لیست — Socket.io (بدون رفرش/poll)

بعد از بارگذاری اولیه با REST، به namespace `/operator` وصل شو. از این به
بعد هر تغییری در صف — مکالمه‌ی تازه، پیام جدید روی یک مکالمه‌ی موجود، یا
حذف‌شدن از صف — **تکی** (نه کل لیست) به تو می‌رسد؛ خودت آن یک آیتم را در
state لوکال پچ کن.

```js
import { io } from "socket.io-client";

const socket = io(`${WS_BASE_URL}/operator`, {
  auth: { token: adminAccessToken }, // همان JWT پنل ادمین
  query: { tenantKey: "default" },   // فعلاً همیشه "default"
});
```

⚠️ اگر توکن نامعتبر باشد یا نقش کاربر اپراتور نباشد، سرور بلافاصله
`socket.disconnect(true)` می‌زند — یعنی روی کلاینت `disconnect` را می‌گیری
بدون این‌که هیچ‌وقت واقعاً «متصل» حساب شده باشی.

### رویدادهایی که گوش می‌دهی

| رویداد | چه‌وقت | کاری که باید بکنی |
|---|---|---|
| `queue:new` | یک مکالمه‌ی تازه به اپراتور ارجاع شد (AI جواب نداد یا مشتری خودش خواست پشتیبانی) | این آیتم را به **بالای** لیست اضافه کن + یک نوتیفیکیشن/صدا برای اپراتور |
| `queue:update` | مکالمه‌ای که از قبل در لیست بود، تغییر کرد (پیام تازه‌ی مشتری، یا اپراتور دیگری جواب داد) | آیتم موجود با همین `id` را در لیست پیدا و جایگزین کن؛ اگر لیست بر اساس `lastMessageAt` مرتب است، به بالا منتقلش کن |
| `queue:removed` | مکالمه از صف خارج شد (بسته شد، حذف شد، یا اپراتور آزادش کرد) | آیتم با همین `id` را از لیست حذف کن |

هر سه رویداد (به‌جز `queue:removed` که فقط `{ id }` دارد) همان شکل آیتمِ
پاسخ REST بالا را دارند:
```json
{ "id": "...", "channel": "...", "status": "...", "customer": {...}, "lastMessageAt": "..." }
```

### رویدادی که می‌فرستی — پاسخ‌دادن از همین‌جا

می‌توانی به‌جای `POST /api/operator/reply`، مستقیم از سوکت هم جواب بدهی
(هر دو مسیر دقیقاً یک پیاده‌سازی مشترک دارند، فرقی در رفتار ندارند):

```js
socket.emit("operator:reply", {
  conversationId: "665f1a2b3c4d5e6f7a8b9c0d",
  text: "بله موجوده، همین امروز ارسال می‌شه",
  replyToMessageId: "665f1a2b3c4d5e6f7a8b9c0e", // اختیاری — رجوع به بخش «ریپلای به پیام مشخص»
});
```

اگر خطایی رخ بدهد (مثلاً conversationId نامعتبر)، رویداد `error` با
`{ message }` می‌رسد.

### ریپلای به یک پیام مشخص (نه فقط آخرین پیام)

هر پیام (چه از مشتری، چه از موتور، چه از اپراتور) یک `id` دارد. اگر
اپراتور بخواهد دقیقاً به یک پیام مشخص از تاریخچه پاسخ بدهد (نه لزوماً
آخرین پیام)، همان `id` را به‌عنوان `replyToMessageId` بفرست — هم در
`POST /api/operator/reply` هم در `socket.emit("operator:reply", ...)`.

- برای **تلگرام**: این به quote-کردن بومی تلگرام (reply در همان چت) تبدیل
  می‌شود — مشتری می‌بیند اپراتور دقیقاً به کدام پیامش جواب داده.
- برای **وب‌سایت**: چون ویجت وب‌سایت اصلاً مفهوم ریپلای به یک پیام مشخص
  را ندارد (فقط یک لیست خطی است)، این مقدار همراه رویداد `operator:reply`
  فرستاده می‌شود (`{ conversationId, text, replyToMessageId }`) تا اگر
  خواستی در UI پیام quote‌شده را نشان بدهی، بتوانی — ولی اجباری نیست.

خودِ پیام‌های موتور (ENGINE) هم همیشه `replyToMessageId` را به همان پیام
مشتری که جوابش را داده‌اند ست می‌کنند — یعنی از همین حالا کل تاریخچه‌ی هر
مکالمه thread‌پذیر است، حتی اگر UI فعلی‌ات ازش استفاده نکند.

## ۳. رفتار «sticky» — چرا مهم است اپراتور این را بداند

به محض این‌که یک مکالمه `NEEDS_OPERATOR` یا `WITH_OPERATOR` شد، لایه‌های
خودکار (کلمات رزرو شده + AI) **دیگر هیچ‌وقت خودشان دوباره وارد نمی‌شوند** —
حتی اگر مشتری در همین حین پیام‌های بیشتری بفرستد که کلمات رزرو شده دارند.
این یک تصمیم عمدی است: وقتی یک مکالمه به انسان سپرده شد، نباید ربات یهو
وسط کار بپرد و جواب بدهد.

**تنها راه برگشت به حالت خودکار:**

### `POST /api/operator/conversations/:conversationId/release`

مکالمه را دوباره `OPEN` می‌کند و از اپراتور فعلی جدا می‌کند — از پیام بعدی
مشتری، لایه‌های خودکار دوباره کار می‌کنند. مثال استفاده: اپراتور یک سوال
ساده را دستی جواب داد و می‌خواهد بقیه‌ی مکالمه دوباره خودکار باشد.

### `POST /api/operator/conversations/:conversationId/close`

مکالمه را می‌بندد (نه release — یعنی این نخِ مکالمه تمام شده؛ پیام بعدی
مشتری یک مکالمه‌ی تازه می‌سازد که از OPEN شروع می‌شود).

### `DELETE /api/operator/conversations/:conversationId`

مکالمه و همه‌ی پیام‌هایش را کامل حذف می‌کند (غیرقابل بازگشت).

## ۴. رسانه‌ی تلگرام (عکس/صوت) — بدون ذخیره‌سازی

وقتی مشتری در تلگرام عکس یا پیام صوتی بفرستد، موتور نمی‌تواند محتوایش را
بفهمد — پس **بلافاصله و خودکار** مکالمه به اپراتور ارجاع داده می‌شود
(بدون اینکه AI/کلمات رزرو شده اصلاً درگیرش کنند). در لیست پیام‌های آن
مکالمه یک پیام با محتوایی مثل «📷 مشتری یک عکس فرستاد» می‌بینی، با
`metadata.telegramFileId`.

خودِ فایل هیچ‌وقت روی سرور ما ذخیره نمی‌شود. برای نمایشش:

### `GET /api/operator/conversations/:conversationId/messages/:messageId/media`

بایت‌های واقعی فایل را (با `content-type` درست) مستقیم برمی‌گرداند — هر
بار که این آدرس را باز کنی، تازه از سرورهای تلگرام خوانده می‌شود. کافی
است در پنل یک `<img src="...">` یا `<audio src="...">` به همین آدرس بدهی
(همراه با هدر Authorization، یا از طریق یک پروکسی که خودت هدر را اضافه
می‌کند چون تگ `<img>` هدر سفارشی نمی‌فرستد — راه ساده: fetch کن، به
blob URL تبدیل کن، بعد به `src` بده).

```js
async function loadMedia(conversationId, messageId, token) {
  const res = await fetch(
    `${API_BASE_URL}/operator/conversations/${conversationId}/messages/${messageId}/media`,
    { headers: { Authorization: `Bearer ${token}` } }
  );
  const blob = await res.blob();
  return URL.createObjectURL(blob);
}
```

## ۵. مثال کامل جریان کار پنل

1. لاگین با همان حساب ادمین سایت اصلی → access token را نگه دار.
2. `GET /api/operator/queue` → لیست اولیه را رندر کن.
3. اتصال Socket.io به `/operator` با همان توکن.
4. `queue:new` / `queue:update` / `queue:removed` → لیست را لوکال patch کن (نه رفرش کامل).
5. کلیک روی یک آیتم → `GET /api/operator/conversations/:id` → تاریخچه را نشان بده.
6. جواب اپراتور → یا `POST /api/operator/reply` یا `socket.emit("operator:reply", ...)`.
7. اگر پیام مشتری عکس/صوت بود → دکمه‌ی «نمایش رسانه» → همان fetch بالا.
8. دکمه‌های مدیریتی روی هر مکالمه: «آزاد کن» (release)، «ببند» (close)، «حذف» (delete).
